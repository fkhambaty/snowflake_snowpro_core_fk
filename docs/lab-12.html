Before Step 1

Kai: “Is a stream a table I query forever?”

1 Curated table + stream on LAB.ORDERS

What this does: Builds the target table and a change feed. Streams need a source table that already exists (Lab 00 sample data).

SQL · stream
USE ROLE ROLE_CORE_LAB_ADMIN;
USE WAREHOUSE WH_CORE_XS;
USE DATABASE ALPINE_RETAIL;
USE SCHEMA PIPELINE;

CREATE OR REPLACE TABLE PIPELINE.ORDERS_CURATED (
  ORDER_ID NUMBER, CUSTOMER_ID NUMBER,
  ORDER_TS TIMESTAMP_NTZ, AMOUNT_USD NUMBER(10,2),
  STATUS STRING, UPDATED_AT TIMESTAMP_NTZ DEFAULT CURRENT_TIMESTAMP()
);

CREATE OR REPLACE STREAM PIPELINE.STR_ORDERS_CDC
  ON TABLE LAB.ORDERS;
✓ SHOW STREAMS should list STR_ORDERS_CDC

3 CREATE TASK + EXECUTE once

What this does: Schedules a MERGE from the stream. Bootstrap granted EXECUTE TASK on the account. Tasks start suspended — resume, execute once for the lab, then suspend so you don’t burn credits hourly.

SQL · task (create)
CREATE OR REPLACE TASK PIPELINE.TASK_MERGE_ORDERS
  WAREHOUSE = WH_CORE_XS
  SCHEDULE = '60 MINUTE'
AS
  MERGE INTO PIPELINE.ORDERS_CURATED t
  USING (
    SELECT * FROM PIPELINE.STR_ORDERS_CDC
  ) s
  ON t.ORDER_ID = s.ORDER_ID
  WHEN MATCHED AND s.METADATA$ACTION = 'DELETE' THEN DELETE
  WHEN MATCHED AND s.METADATA$ISUPDATE THEN UPDATE SET
    t.STATUS = s.STATUS, t.AMOUNT_USD = s.AMOUNT_USD,
    t.UPDATED_AT = CURRENT_TIMESTAMP()
  WHEN NOT MATCHED AND s.METADATA$ACTION = 'INSERT' THEN INSERT
    (ORDER_ID, CUSTOMER_ID, ORDER_TS, AMOUNT_USD, STATUS)
    VALUES (s.ORDER_ID, s.CUSTOMER_ID, s.ORDER_TS,
            s.AMOUNT_USD, s.STATUS);
SQL · execute + suspend
ALTER TASK PIPELINE.TASK_MERGE_ORDERS RESUME;
EXECUTE TASK PIPELINE.TASK_MERGE_ORDERS;
SHOW TASKS LIKE 'TASK_MERGE%' IN SCHEMA PIPELINE;
SELECT * FROM PIPELINE.ORDERS_CURATED ORDER BY ORDER_ID;
ALTER TASK PIPELINE.TASK_MERGE_ORDERS SUSPEND;

Morgan: “Why not Dynamic Tables for everything?”

4 Dynamic Table (or study the comment)

What this does: Declares a continuously refreshed aggregate. If your edition blocks CREATE DYNAMIC TABLE, leave it commented — still say the TARGET_LAG story out loud.

SQL · dynamic table
CREATE OR REPLACE DYNAMIC TABLE PIPELINE.DT_ORDERS_DAILY
  TARGET_LAG = '1 minute'
  WAREHOUSE = WH_CORE_XS
AS
SELECT DATE_TRUNC('day', ORDER_TS) AS ORDER_DAY,
       STATUS,
       COUNT(*) AS ORDER_CNT,
       SUM(AMOUNT_USD) AS AMOUNT_SUM
FROM LAB.ORDERS
GROUP BY 1, 2;

SHOW DYNAMIC TABLES LIKE 'DT_ORDERS%' IN SCHEMA PIPELINE;
✓ DT created — or you can explain TARGET_LAG without running it

Exam presses further — say these out loud

Q1. What is a stream “offset” in plain English?

Say: The bookmark of which changes you’ve already consumed. Reading the stream in a consuming DML advances it so the next run only sees newer changes.

Q2. What is a task graph?

Say: Tasks can depend on other tasks (AFTER …). Root task has a schedule; children run when parents succeed — Snowflake-native DAG without an external orchestrator.

Q3. What drives Dynamic Table cost?

Say: Refresh compute on the warehouse you assign, driven by how often lag requires refresh and how heavy the SELECT is. Tighter TARGET_LAG → more frequent work.

Q4. When prefer dbt vs Dynamic Tables?

Say: Prefer DT for simple Snowflake-native continuous transforms with a lag SLO. Prefer dbt when you need Git-centric models, tests, docs, and complex multi-project DAGs. Exam may highlight Snowflake-native DT.

Q5. Snowpipe vs stream — can a stream replace Snowpipe?

Say: No. Streams track DML on tables already in Snowflake. Snowpipe loads files from stages/storage. Different layer of the pipeline.
