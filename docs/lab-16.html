AT vs BEFORE — same idea, different pointer

1 · Past AT(…) inclusive of that moment
2 · Exclusive BEFORE(…) state just before stmt/time
3 · Clone CLONE … AT new table from old history

You can point with TIMESTAMP, OFFSET (seconds), or STATEMENT (query id). Exam loves: BEFORE is exclusive of that statement.

1 Scratch table + a bad edit

What this does: Creates LAB.SCRATCH_TT, inserts a good row, then overwrites it so we have history to query.

SQL · scratch + bad UPDATE
USE ROLE ROLE_CORE_LAB_ADMIN;
USE WAREHOUSE WH_CORE_XS;
USE DATABASE ALPINE_RETAIL;
USE SCHEMA LAB;

CREATE OR REPLACE TABLE SCRATCH_TT (
  ID NUMBER, NOTE STRING
);
INSERT INTO SCRATCH_TT VALUES (1, 'v1-original');
UPDATE SCRATCH_TT SET NOTE = 'v2-oops-bad-edit' WHERE ID = 1;
✓ Current row shows v2-oops-bad-edit

Before Step 2

Kai: “Is AT a backup restore?”

2 Query the past with AT

What this does: Reads the table as of ~60 seconds ago (bump the offset if your session was slow).

SQL · Time Travel SELECT
SELECT * FROM SCRATCH_TT AT(OFFSET => -60);

-- Exam syntax awareness (use a real query_id when you have one):
-- SELECT * FROM SCRATCH_TT BEFORE(STATEMENT => '<query_id>');
✓ You should see v1-original (or empty if offset > age of insert — raise offset)

3 Retention + clone at timestamp

What this does: Shows the retention parameter, sets 1 day on the scratch table, and clones history into a new table.

SQL · retention + clone AT
SHOW PARAMETERS LIKE 'DATA_RETENTION_TIME_IN_DAYS'
  IN TABLE SCRATCH_TT;

ALTER TABLE SCRATCH_TT SET DATA_RETENTION_TIME_IN_DAYS = 1;

CREATE OR REPLACE TABLE SCRATCH_TT_CLONE_AT
  CLONE SCRATCH_TT AT(OFFSET => -60);

SELECT * FROM SCRATCH_TT_CLONE_AT;
✓ Clone table exists; live SCRATCH_TT still on the bad edit

Sam: “What if they DROP the whole table?”

4 DROP then UNDROP

What this does: Deletes the table object, then brings it back from Time Travel history.

SQL · DROP / UNDROP
DROP TABLE SCRATCH_TT;

UNDROP TABLE SCRATCH_TT;

SELECT * FROM SCRATCH_TT;
✓ Table is back; row still whatever it was at drop time

Exam presses further — say these out loud

Cover each answer before you open it. Domain 5 loves these traps.

Q1. Time Travel vs Fail-safe — who can recover, and with what?

Say: Time Travel is user-driven SQL (AT/BEFORE, UNDROP, clone-at-time) inside retention. Fail-safe is after TT expires: ~7 days on permanent tables, recoverable only via Snowflake Support — not a SELECT.

Q2. Standard vs Enterprise Time Travel length?

Say: Standard defaults to 1 day. Enterprise (and higher) can configure up to 90 days via DATA_RETENTION_TIME_IN_DAYS. Distractor: “Standard supports 90-day TT.”

Q3. Do transient tables have Fail-safe?

Say: No. Transient and temporary tables do not have Fail-safe. They may have short Time Travel; do not plan Support recovery the same way as permanent tables.

Q4. What can you UNDROP?

Say: DATABASE, SCHEMA, and TABLE (and some related objects in the same spirit) within the Time Travel window. After retention ends, UNDROP fails — Fail-safe path is Support, not UNDROP.

Q5. Does raising retention to 90 days cost anything?

Say: Yes — retained historical micro-partitions are billable storage. Use long retention where recovery justifies cost; keep scratch/lab tables at 0–1 day.
